## Owner-approved demo backup policy (2026-11-03)

Owner explicitly authorized release to main, read-only production backup and Google Drive storage. My Drive folder SheetOps: https://drive.google.com/drive/folders/1F4PM1lwEwbRDu2gU-hFW5yhaGaHCg6FO. Both existing production/development-named and staging spreadsheets were moved there; IDs and individual sharing were preserved. Folder metadata reports shared=false.

Owner chose weekly Sunday 23:00 Asia/Bangkok (UTC+7), replacing the earlier proposed daily cadence. Codex local automation `backup-sheetops-ch-nh-t-23h` runs the backup script then uploads encrypted archive, key and manifest through the authenticated Drive connector. This is local scheduling: the computer, Codex, Docker, network and private connection configuration must be available. It is not an unattended cloud backup SLA; a missed run increases the recovery gap beyond the nominal seven-day interval. No backup deletion/retention pruning is authorized.

For this synthetic demo, owner explicitly requested the decryption key in the SAME private Drive folder as the encrypted archive. This overrides the earlier recommendation to separate keys. Anyone with access to both can decrypt the backup; do not claim key separation or protection from compromise of that Drive account. Do not broaden folder sharing. Do not log or commit key material.

`RUN_DATABASE_BACKUP=1 npm run backup:database` loads only ignored `.env.backup.local` DATABASE_URL. Use the production Session pooler URI, port 5432; Supabase API keys cannot substitute for database credentials. Connection guard pins the production ref. Docker runs official PostgreSQL 17 Alpine pg_dump read-only, custom archive, public/private/auth/supabase_migrations schemas. No host volumes/ports are exposed. Data remains in memory until encrypted; only encrypted archive, key and safe manifest are written under ignored output/backups. The archive listing must include orders/audit/Auth users, and encryption is round-trip checked before success. Separate key per timestamped archive; no overwrites.

Scope limits: excludes Storage object bytes and external configuration/credentials; cluster roles must exist on the prepared Supabase restore target. Full Supabase/Auth restore has not been exercised with this production artifact. pg_restore listing/decryption checks are not a substitute for a full isolated restore. Do not restore over production. CLI initial backup result and Drive file metadata are recorded in PHASE_3_VERIFICATION.md after completion. Direct database hostname DNS failed from Docker; this is why a Session pooler URI is required for this machine.

Free plan was verified through organization metadata. [Supabase documentation](https://supabase.com/docs/guides/platform/backups) reserves managed daily backups for paid plans and recommends CLI exports/offsite copies for Free. Do not claim dashboard backups or PITR are available here.

Owner procedure: install trusted Supabase CLI/PostgreSQL tools; inspect `supabase db dump --help`, `pg_dump --help` and tool versions before use. Use a private environment/pgpass file for database credentials, never URL/password arguments or shell history. Dump schema, roles and data as separate artifacts as appropriate for Supabase-managed schemas. Include application public/private schemas and required Auth recovery metadata in a full production recovery design; exclude managed internals only according to current Supabase restore guidance. Storage objects need a separate backup if introduced. Record migration versions, tool versions, UTC timestamp and row counts.

The active demo policy is weekly Sunday 23:00 UTC+7, per-archive AES-256-GCM encryption and owner-private Drive storage with co-located keys. Nominal recovery gap is up to seven days when runs succeed; missed local runs extend it. Recovery time is not measured for full Supabase. No automatic retention deletion is enabled. Revisit key separation and frequency before introducing real customer data.

Recovery of this script's format: retrieve the matching .pgdump.enc, .key.json and .manifest.json privately. Compare encrypted SHA-256 with the manifest. Parse the 9-byte ASCII SHEETOPS1 header, next 12 bytes nonce, next 16 bytes GCM authentication tag and remaining ciphertext. Decode keyBase64 from the key JSON and decrypt using AES-256-GCM; fail if authentication fails. Compare decrypted SHA-256 with plainSha256 and inspect using pg_restore --list. Decrypt in memory or an access-restricted temporary environment; never print the key or archive contents. Restore only to a prepared isolated target with matching managed roles/extensions, according to current Supabase guidance; preserve grants. Verify application schemas, Auth identities, exact order totals, audits, RLS and login before considering cutover. Do not assume a generic empty PostgreSQL instance can reproduce Supabase Auth infrastructure.

Restore drill: create a disposable isolated staging database with synthetic users/orders, seed via app/RPC so audit is valid, record baseline counts/checksums and RLS. Export and encrypt that fixture, restore into a second empty isolated target using current Supabase restore ordering (roles/schema/data, identities/sequences, grants/triggers/functions), then compare 300/2000-row counts, exact VND totals, indexes, foreign keys, audit, sessions/roles and denied Viewer writes. Measure elapsed restore time; record artifact digest without content or credentials. Never restore over production or a shared staging database. A synthetic-only logical restore does not prove full Auth disaster recovery; test that separately before sign-off.

Incident recovery: freeze writes with owner approval, select last verified artifact, provision a new target (no billing change without approval), restore/verify in isolation, reconcile post-backup changes, obtain approval before cutover and rotate affected secrets privately. Keep the prior environment until reconciliation and rollback decision. Application rollback does not reverse migrations or recover lost rows.

Owner handover explanation: offsite means a copy outside the Supabase project, here the private Drive folder. Encryption requires the matching key to unlock the archive. The owner intentionally chose the same folder for demo; Drive account access therefore grants access to both. Loss of the only key makes its archive unrecoverable. Secrets, plaintext dumps and backup files must never enter Git.
